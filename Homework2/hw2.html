Wallet seed → Ethereum address

An Ethereum wallet turns a list of words into an address through a chain of standards: BIP-39, BIP-32, BIP-44, secp256k1, Keccak-256 and EIP-55. On this page I implement the chain step by step, check it against the official test vectors, analyse the statistical behaviour of its outputs and place each piece in its historical context.

1.1

Key generation: entropy and mnemonic (BIP-39)

This is the only step of the whole pipeline that uses randomness. The wallet takes ENT = 128 to 256 random bits (the entropy) from a secure random number generator, and everything after this is computed deterministically from these bits. This is the key generation part.

BIP-39 then turns the entropy into a form that a person can write down. It adds a checksum, i.e. the first CS = ENT/32 bits of SHA-256(entropy), splits everything into groups of 11 bits and uses each group as an index in a fixed list of 2048 words (211 = 2048). The words are therefore just an encoding of the entropy, and the last few bits are a checksum.

1.2

Mnemonic → seed (BIP-39)

The phrase is not used directly as a key. BIP-39 first turns it into a 512-bit seed using PBKDF2, a key derivation function that applies HMAC-SHA512 many times in a row:

seed = PBKDF2(HMAC-SHA512, password = phrase, salt = "mnemonic" ‖ passphrase, 2048, 512 bits)

The 2048 iterations make every guess more expensive for an attacker. The optional passphrase goes into the salt, so the same words with a different passphrase give a completely different wallet. (Both strings are also Unicode-normalised (NFKD) first, so that the same text always gives the same bytes.)

1.3

Seed → master key (BIP-32)

BIP-32 introduces hierarchical deterministic (HD) wallets: a single seed generates a whole tree of key pairs. The root of the tree comes from one HMAC-SHA512:

I = HMAC-SHA512(key = "Bitcoin seed", data = seed),   I = IL ‖ IR

The left 256 bits are the master private key, and the right 256 bits are the chain code, an extra value used to derive the child keys. The string "Bitcoin seed" is fixed by the standard, and Ethereum wallets use it as well, despite the name.

1.4

Derivation path (BIP-44)

BIP-32 specifies how to compute child i of a node, but not which branch of the tree to use. BIP-44 fixes this, so that the same phrase gives the same accounts in every wallet that follows it:

m / purpose′ / coin_type′ / account′ / change / address_index

For Ethereum the path is m/44′/60′/0′/0/i: 44 means BIP-44, 60 is the number registered for Ether in SLIP-44, and the last index counts the accounts. This is also the default path used by MetaMask.

The prime (′) means the child is hardened. The difference is in what goes into the HMAC:

hardened (i ≥ 2³¹): I = HMAC-SHA512(cpar, 0x00 ‖ kpar ‖ i)
normal (i < 2³¹): I = HMAC-SHA512(cpar, Kpar ‖ i)
ki = (IL + kpar) mod n,   ci = IR

A normal child only needs the parent's public key and chain code, so child public keys can be derived without knowing any private key. A hardened child needs the parent's private key. Like PBKDF2, this is key derivation: it is deterministic and does not add any new randomness.

1.5

Private key → public key (secp256k1)

The private key k is a number between 1 and n − 1. The public key is the point K = k·G on secp256k1, which is the same equation as the toy curve of Exercise 1, just over a 256-bit prime field:

y² ≡ x³ + 7 (mod p),   p = 2²⁵⁶ − 2³² − 977
n ≈ 1.158 × 10⁷⁷ (number of points generated by G)

Computing K from k takes around 256 doublings and additions, while recovering k from K is the elliptic-curve discrete logarithm problem. This is public-key cryptography: K can be shared, and anyone who knows it can check signatures made with k (ECDSA). The point is then written as 0x04 ‖ x ‖ y (65 bytes), which is just an encoding.

1.6

Public key → address (Keccak-256)

The address is the last 20 bytes of the Keccak-256 hash of the public key, without the 0x04 at the beginning:

address = Keccak-256(x ‖ y)[12 … 31]

The hash turns the 64-byte point, which has a lot of structure, into a short identifier that looks random (see Part II). The highlighted part below shows the 20 bytes that form the address.

1.7

Checksummed address (EIP-55)

A plain hex address has no redundancy, so a single mistyped character simply produces another valid address. EIP-55 adds a checksum without making the address longer, by using upper and lower case for the letters a–f:

h = Keccak-256(address in lowercase hex, as ASCII text)
letter at position i → uppercase if the i-th hex digit of h is ≥ 8

Each cell shows a character of the address with the matching digit of h under it. Filled cells are letters that became uppercase, outlined cells are letters that stayed lowercase, and digits carry no information. So the result is both an encoding (mixed-case hex) and a checksum. Since hexadecimal is case-insensitive, programs that do not check EIP-55 can still read the address normally.

    Part II

    Six kinds of operation

    The pipeline mixes operations that have very different goals. Separating them makes it much easier to understand why each standard exists.

    Operation What it does Where in the pipeline Secret? Reversible?
    Key generation Creates a new secret from randomness. What matters is the entropy: the secret has to be unpredictable. The 128–256 random bits of BIP-39 (1.1). It happens only once, when the wallet is created. Secret. Nothing to reverse: the output is pure randomness.
    Key derivation Computes new keys from an existing secret, in a deterministic way. The same input always gives the same keys, so a single backup is enough to recover all of them. PBKDF2 in BIP-39 (1.2), HMAC-SHA512 in BIP-32 (1.3), the BIP-44 path (1.4). Outputs are secret. One-way for hardened children. For normal children, if a child private key leaks together with the parent's public key and chain code, the parent private key can be recovered. This is why BIP-44 hardens the first three levels.
    Public-key cryptography Links a private key to a public key, so others can verify signatures without learning the secret. secp256k1, K = k·G (1.5); ECDSA signatures when sending transactions. k secret, K public. One-way (ECDLP).
    Hashing Maps data of any length to a fixed-length output that looks random; it should be hard to invert and hard to find collisions. Keccak-256 for the address (1.6) and inside EIP-55; SHA-256 for the BIP-39 checksum; SHA-512 inside HMAC and PBKDF2. Public algorithm, no key. One-way.
    Checksum Adds some redundancy to catch accidental mistakes. It does not protect against an attacker, who can simply recompute it. The 4–8 checksum bits of BIP-39 (1.1); the upper/lower case of EIP-55 (1.7). Public. Anyone can check it.
    Encoding Writes the same information in a different form, with no security purpose. Bits → words (BIP-39), bytes → hex, the 0x04 ‖ x ‖ y format, the mixed-case form of EIP-55. Public. Fully reversible.

    Some steps are a mix of two kinds: a BIP-39 phrase is an encoding with a checksum inside, and EIP-55 is an encoding where the letter case carries a checksum computed with a hash. In my opinion the most important distinction in practice is between generation and derivation: only generation needs a good source of randomness, and everything after it can be recomputed from the phrase at any time.

    Statistical properties

    These experiments run in the browser when the page loads, and each one can be repeated with its button. They check the properties that each step is supposed to have: an unpredictable input, outputs that look uniform, no useful relation between similar inputs, and a known rate of error detection.

    3.1

    Entropy and the BIP-39 checksum

    The security of the whole wallet depends on the entropy of the first step: with 128 bits an attacker would have to try about 2128 ≈ 3.4 × 1038 phrases. The checksum bits do not add any entropy; they only make most mistyped phrases invalid.

    Avalanche effect of Keccak-256

    3.4

    EIP-55 as an error-detecting code

    The checksum is only in the letters. A hex digit is a letter with probability 6/16, so the number of letters in an address follows B(40, 6/16), with mean 15: on average an address carries 15 check bits. Over random addresses I get a mean of letters.

    After a typo the hash changes completely, so each letter has the right case only with probability ½ while digits always pass. A mistyped address is therefore accepted with probability

    P = (10/16 + 6/16 · ½)40 = (13/16)40 ≈ 0.0247%

    Part III

    Historical context

    The basic cryptographic tools are much older than the wallet standards built on top of them. The dates refer to when each one was first published or standardised.

    1. 1977
      RSA

      Rivest, Shamir and Adleman present the first practical public-key cryptosystem.

    2. 2000
      secp256k1 (SEC 2)

      The curve is published by the Standards for Efficient Cryptography Group (version 1.0, September 2000).

    3. 2001
      SHA-2 (SHA-256, SHA-512)

      Designed by the NSA, published as a draft in 2001 and officially standardised by NIST in August 2002.

    4. 2012
      BIP-32 · HD wallets

      Pieter Wuille defines hierarchical deterministic key derivation (February 2012).

    5. 2012
      Keccak wins the SHA-3 competition

      NIST picks Keccak (by Bertoni, Daemen, Peeters and Van Assche) as the winner on 2 October 2012.

    6. 2013
      BIP-39 · mnemonic code

      Mnemonic phrases and how to turn them into a seed (September 2013).

    7. 2014
      BIP-44 · multi-account hierarchy

      Standard derivation paths for many coins and accounts (April 2014).

    8. 2015
      Ethereum launches

      The first release (Frontier) goes live on 30 July 2015, already using Keccak-256.

    9. 2015
      SHA-3 (FIPS 202)

      NIST approves SHA-3 on 5 August 2015, with a padding rule that is different from the original Keccak.

    10. 2016
      EIP-55 · checksummed addresses

      Vitalik Buterin and Alex Van de Sande propose the mixed-case checksum (January 2016).

    The chronological order reveals a layering. Public-key cryptography (1977) and the hash functions (2001–2015) are general tools designed by researchers and standards bodies. The BIPs (2012–2014) came later from the Bitcoin community, as conventions on how to manage keys using those tools, and Ethereum reused them with its own coin type. Ethereum was also launched a few days before FIPS 202 was approved, and it kept the padding of the original Keccak submission: this is why it uses Keccak-256 and not SHA3-256. EIP-55 arrived afterwards to fix a practical problem, since plain hex addresses had no way to detect typos. In the timeline, filled dots are the main standards from the assignment and empty dots are the extra steps I added to complete the picture.

    SHA-2 vs Keccak / SHA-3

    Both are families of cryptographic hash functions standardised by NIST, about thirteen years apart, but their internal designs are completely different.

    SHA-2 (SHA-256, SHA-512) Keccak / SHA-3
    Construction Merkle–Damgård: the message is split into blocks and a compression function processes them one after the other. Sponge: a fixed permutation first "absorbs" the input into a big internal state and then "squeezes" the output out of it.
    Internal size SHA-512: 1024-bit blocks, 64-bit words, 80 rounds. 1600-bit state, 24 rounds. For a 256-bit output: rate 1088 bits, capacity 512 bits.
    Length extension Vulnerable: from H(m) it is possible to compute H(m ‖ padding ‖ x) without knowing m. HMAC, used in BIP-32 and PBKDF2, is not affected thanks to its nested construction (the inner hash is hashed again together with the key). Not vulnerable, because part of the state (the capacity) is never given as output.
    Role in the pipeline SHA-256 for the BIP-39 checksum; SHA-512 inside PBKDF2 (BIP-39) and HMAC (BIP-32). Keccak-256 for the address and for the EIP-55 checksum.

    Keccak-256 is not SHA3-256

    Ethereum's Keccak-256 and the standard SHA3-256 use the same permutation, rate and capacity, and differ only in the padding. Before the usual 10…01 padding, FIPS 202 adds two extra bits 01 (domain separation), so the first padding byte becomes 0x06 instead of Keccak's 0x01. Such a small change is enough to give completely different outputs, as the live comparison on the right shows.

    Some libraries and older Ethereum APIs call Keccak-256 "sha3", which is a source of confusion: the function actually used should always be checked, because they are not interchangeable.

    Why so many primitives instead of one

    Each step solves a different problem, and no single algorithm has all the required properties.

    Component Purpose Why another primitive could not do it
    BIP-39 / BIP-32 / BIP-44 KEY MANAGEMENT
    One backup that a person can read, an unlimited tree of keys, and the same accounts in every compatible wallet.     		A hash or a curve alone does not provide a backup format or a standard way to organise many keys. These are rules on how to use the primitives, not primitives themselves.
    secp256k1 PUBLIC-KEY CRYPTO
    A public key that others can use to check signatures made with the private key.     		A hash function has no public/private key pair: verifying a value requires the input, which here would be the secret.
    Keccak-256 HASHING
    A short, fixed-length identifier that looks random, derived from the public key.     		The curve point is long (64 bytes) and has structure, so it is not suitable as an identifier and doesn't look random.
    EIP-55 CHECKSUM
    Catches typing mistakes without making the address longer, and still works with old software.     		The other primitives are about security against attackers; none of them deals with accidental mistakes when someone copies an address by hand.

    The pipeline is therefore a stack of separate layers: randomness creates the secret, derivation organises it into keys, public-key cryptography lets the owner prove they control an account, hashing gives the account a short name, and the checksum protects that name from typos. Each layer can be studied, tested and, if necessary, replaced on its own, and each one is a well-known standard instead of one single algorithm forced to do things it was not designed for.

    The statistical experiments match this split. Entropy only matters in the generation step; uniformity and the avalanche effect are the expected behaviour of the derivation and hashing steps; and the checksums are described by how often they catch errors: 1 − 1/16 for a random 12-word phrase and about 99.975% for a mistyped EIP-55 address.

Homework 2 · Encryption and cryptanalysis

Toy ECC vs Caesar cipher

In this homework I use the toy elliptic-curve scheme to encrypt and decrypt a short message, and I encrypt the same message with the Caesar cipher. Then I attack both: the Caesar cipher with a statistical analysis of English letter frequencies, the toy scheme with a search over its restricted key space. Comparing the two attacks shows why the first one works whatever the key is, while the second one stops working as soon as the private key is drawn from the full range of secp256k1.

1.1

The toy scheme

In Exercise 1 of Homework 1 I built the key pair on the curve y² = x³ + 7 modulo 17. That curve has only 18 elements, which is not even enough to represent one byte of text, so here I keep everything and change only the field: the equation, the addition formulas and the double-and-add multiplication are the same, but the arithmetic is done modulo the prime of secp256k1, and the base point is its standard generator G (the same one used in Exercise 2).

E :  y² ≡ x³ + 7 (mod p),   p = 2256 − 232 − 977
G = (79be667e…16f81798, 483ada77…fb10d4b8)
n = order of G ≈ 1.158 × 1077 (a prime number)

What makes the scheme a toy is the private key. Instead of being drawn from the whole range {1, …, n − 1}, it is drawn uniformly from {1, …, K} with K = 2b, chosen in the box above (220 by default). This keeps the attacks of Part IV feasible in a browser, and it is the only difference from a real key.

CURVEsecp256k1
FIELD SIZE256 bits
KEY SPACEK = 2

Numbers of 256 bits do not fit in ordinary JavaScript numbers, so the code uses BigInt. To go faster it also stores points in Jacobian coordinates (X, Y, Z), which stand for the point (X/Z², Y/Z³): in this form an addition needs no modular inverse, and only one inverse is computed at the end to go back to (x, y).

1.2

Key generation and role of the keys

The receiver generates the key pair: a private key k chosen at random and the public key Q = k·G, computed with double-and-add as in Exercise 1. Q is published, while k is kept secret. Encryption also needs a third number, a random r chosen by the sender for every block of the message and thrown away afterwards.

Private key k
Public key Q
Key Known by Used for Range
k private receiver only decryption {1, …, K}
Q public everyone encryption point of the curve

The key point is that sender and receiver never need to share a secret: anyone can encrypt with Q, but only the owner of k can decrypt. This is what makes the scheme asymmetric.

1.3

Encoding the message as points

Encryption works with points, so the message first has to become a list of points. I take the UTF-8 bytes of the text (for plain ASCII, one byte per character), so every block is a number m between 0 and 255, and I map it to a point with Koblitz's method:

x = 256·m + j,   j = 0, 1, 2, … until x³ + 7 is a square modulo p
y = (x³ + 7)(p+1)/4 mod p (valid because p ≡ 3 mod 4)

About half of the numbers modulo p are squares, so each attempt succeeds with probability close to ½ and on average two attempts are enough; all 256 attempts fail with probability 2−256. Going back is simply m = ⌊x / 256⌋. This step is an encoding, not encryption: anyone can apply it and undo it.

1.4

Encryption

For every message point M the sender draws a fresh random r and computes two points:

r ← random in {1, …, n − 1}
C1 = r·G
C2 = M + r·Q

The point r·Q looks random and acts as a mask added to M, while C1 is sent together with C2 so that the receiver can rebuild the same mask without knowing r. This is the elliptic-curve version of ElGamal encryption. Since r changes for every block, the same character is encrypted differently each time: the scheme is probabilistic.

Points are written in compressed form (33 bytes: a prefix 02 or 03 for the parity of y, then x). Every byte of the message becomes two points, so the ciphertext is 66 times longer than the message: .

1.5

Decryption

The receiver multiplies C1 by the private key and obtains the same mask that the sender used, because both are equal to (k·r)·G:

S = k·C1 = k·r·G = r·Q
M = C2 − S = C2 + (xS, p − yS)
m = ⌊xM / 256⌋

Without k, computing S from C1 and Q is the elliptic-curve Diffie–Hellman problem, which is believed to be as hard as the ECDLP of Exercise 1. With a restricted k, however, it is enough to find k (Part IV).

const KOB = 256n;
function encode(m) {
  for (let j = 0n; j < KOB; j++) {
    const x = BigInt(m) * KOB + j,
      y2 = md(x ** 3n + 7n),
      y = powMod(y2, (p + 1n) / 4n);
    if ((y * y) % p === y2) return { M: [x, y], j: Number(j) };
  }
  throw new Error("encoding failed");
}
const decode = (M) => Number(M[0] / KOB);

const keyGen = (bits) => {
  const k = 1n + randBelow(2n ** BigInt(bits));
  return { k, Q: mul(k) };
};

function encryptByte(m, Q) {
  const { M, j } = encode(m);
  const r = 1n + randBelow(n - 1n);
  const C1 = mul(r),
    S = mul(r, Q),
    C2 = add(M, S);
  return { m, M, j, r, S, C1, C2 };
}
function decryptPair(C1, C2, k) {
  const S = mul(k, C1),
    M = add(C2, neg(S));
  return { S, M, m: decode(M) };
}

Part II

The Caesar cipher

The same message is now encrypted with one of the oldest ciphers, and the two schemes are compared.

2.1

Encryption and decryption

The Caesar cipher replaces every letter with the one s positions later in the alphabet, starting again from A after Z. Numbering the letters A = 0, …, Z = 25:

Es(x) = (x + s) mod 26,   Ds(y) = (y − s) mod 26

I keep upper and lower case and leave spaces, digits and punctuation unchanged, which is the usual convention. The same key s is used to encrypt and to decrypt, so the cipher is symmetric: sender and receiver have to agree on s in advance. Decrypting with s is the same as encrypting with 26 − s. 

function shift(text, s) {
  s = mod26(s);
  let out = "";
  for (const ch of text) {
    const c = ch.charCodeAt(0);
    if (c >= 65 && c <= 90) out += String.fromCharCode(65 + ((c - 65 + s) % 26));
    else if (c >= 97 && c <= 122) out += String.fromCharCode(97 + ((c - 97 + s) % 26));
    else out += ch;
  }
  return out;
}
const encrypt = (text, s) => shift(text, s);
const decrypt = (text, s) => shift(text, -s);

Procedures and key spaces

Type ASYMMETRIC
Public key Q to encrypt, private key k to decrypt. No secret has to be shared in advance. 		SYMMETRIC
One shared secret s for both directions, which has to be exchanged beforehand over a secure channel.
Encryption Encode each byte as a point M, pick a random r, output (rG, M + rQ): two scalar multiplications per byte. Add s to each letter modulo 26: one addition per letter.
Decryption M = C2 − k·C1, then m = ⌊x/256⌋. It uses a different key from encryption, and r is not needed. Subtract s: the inverse of encryption with the same key.
Key space Toy: K = 2 private keys. A real key has n − 1 ≈ 2256 possible values. The number r is not part of the key, but it is always drawn from the full range. 26 shifts, one of which (s = 0) leaves the text unchanged: 25 useful keys, about 24.6. It cannot be made larger without changing the cipher.
Determinism Probabilistic: the same message gives a different ciphertext every time it is encrypted. Deterministic: the same letter always becomes the same letter.
Size of the ciphertext 66 bytes for each byte of message. Same length as the message, word lengths included.
Statistical properties The ciphertext points look uniformly random and do not reflect the frequencies of the plaintext (2.3). The letter frequencies of the plaintext are kept, only moved by s places (2.3).

The two schemes share the same structure, an encryption that adds a secret value and a decryption that removes it: Caesar adds s to letters modulo 26, the toy scheme adds rQ to points of the curve. The difference is in where the secret comes from. In Caesar it is fixed and the same for every letter, so the structure of the language passes through unchanged. In the toy scheme the mask is new for every block and can only be rebuilt from C1 with the private key.

Part III

Statistical cryptanalysis of the Caesar cipher

With only 26 keys the Caesar cipher could be broken by hand, but the interesting question is how a program can recognise the right key automatically, using nothing but the statistics of the language.

3.1

The reference corpus

The attack needs to know what normal text looks like. As the reference corpus I use two public-domain English novels from Project Gutenberg, Alice's Adventures in Wonderland (Lewis Carroll, 1865) and The Man Who Was Thursday (G. K. Chesterton, 1908), stored in corpus.js. From them I estimate the probability pc of each letter and the probability of each pair of consecutive letters, which is used in 3.3.

For the tests I use a third book by a different author, Persuasion (Jane Austen, 1818), so that the attack is never evaluated on the same text it learned from.

The chart shows the well-known shape of English: E, T and A at the top, J, Q, X and Z almost absent. This uneven distribution is what makes the attack possible: if all letters were equally likely, shifting them would change nothing and the frequencies would say nothing about the key.

3.2

Frequency analysis with the χ² statistic

The algorithm I implemented works in four steps:

  1. Count how many times each letter appears in the ciphertext, Oc, with N letters in total; everything that is not a letter is ignored.
  2. For every candidate key s = 0, …, 25, the decrypted text would contain letter c exactly O(c + s) mod 26 times, so there is no need to decrypt anything.
  3. Measure how far these counts are from English with Pearson's statistic: χ²(s) = Σc (O(c+s) mod 26 − N pc)² / (N pc).
  4. Return the key with the best fit, ŝ = argmin χ²(s).

Step 3 is a goodness-of-fit test. For the right key the decrypted text is English and χ² stays around its 25 degrees of freedom (critical value 37.65 at 5%), while a wrong key moves the frequent letters onto rare ones and makes χ² grow very quickly. The test is only approximate here: the χ² distribution needs about 5 expected counts per letter, which for Z or Q means thousands of letters, so for short texts I use χ² only as a score to rank the keys.

The default ciphertext is the encrypted message of 2.1, and a random excerpt of the test text can be generated with the button. The text can also be edited freely. 

function chi2(O, N, p, s) {
  let x = 0;
  for (let c = 0; c < 26; c++) {
    const E = N * p[c],
      o = O[(c + s) % 26];
    x += ((o - E) * (o - E)) / E;
  }
  return x;
}

3.3

Alternative approaches

Exhaustive key search. With 26 keys one can simply decrypt with all of them and look for the candidate that reads as English, as in the table on the side for the current ciphertext. A person does this without effort, but for a program the search alone is not enough: it also needs a way to recognise English, i.e. a score. The other methods are exactly such scores, and all of them still try the 26 keys.

Letter-frequency analysis. The simplest version assumes that the most frequent letter of the ciphertext is E, so ŝ = cmax − 4 mod 26. It uses one number out of 26. The χ² version of 3.2 uses the whole distribution.

n-gram scoring. Instead of single letters, it scores each candidate by the log-likelihood of its pairs of consecutive letters (bigrams) under the model estimated from the corpus:

B(s) = Σi log P(xi xi+1),   P(ab) = (nab + 1) / (N2 + 676)

where nab counts the pair ab in the corpus and the +1 (Laplace smoothing) avoids log 0 for pairs never seen. This also uses the order of the letters: TH and HE are very common, while QZ never appears. The key with the largest B(s) is chosen.

3.4

Ciphertexts of different lengths

To measure how well the three methods work, for each length L I take random excerpts of L consecutive letters from Persuasion, encrypt each with a random key and count how often each method recovers it. With this many trials the standard error of each rate, √(p(1 − p)/T), is at most percentage points.

χ² recovers the key of the time with 10 letters, with 20 and with 50, so from a few dozen letters on it practically never fails. The bigram score is better on short texts ( with 10 letters), because every letter is judged together with its neighbour and carries more information. The naive method is much worse: even with 100 letters E is the most frequent letter only of the time.

The key itself has no effect on the result: changing s only relabels the 26 candidates, so whether the attack succeeds depends only on the plaintext. What matters is how many letters are available and how typical they are.

3.5

Effectiveness and limitations

On ordinary English text of a few dozen letters the attack is essentially always successful, and it costs almost nothing: the letters are counted once, and then 26 sums of 26 terms are computed. Its limits come from the assumptions it makes, and the table on the side tests some of them, all encrypted with s = 7.

  • Short texts. With a handful of letters the observed frequencies are mostly noise. With 7 letters no method finds the key, and with 11 letters χ² fails while the bigram score still succeeds.
  • Atypical texts. The model assumes an average text. A text written without the letter E defeats the naive method, although χ² still succeeds because the other 25 letters are enough. A text full of rare letters (J, Q, X, Z) fools χ² even with almost 80 letters, while the bigram score, which looks at combinations of letters, still works.
  • Known language. The model is English. On an Italian sentence it still works, because the two languages share many frequent letters (E, A, O, I, N), but the fit is worse (the smallest χ² is twice that of the longer English sentence), and a language with a different alphabet or very different frequencies would need its own corpus.
  • Only for this cipher. The attack works because the whole text is shifted by the same amount and there are only 26 keys to try. For a general substitution of the alphabet (26! ≈ 4 × 1026 keys) frequencies still help but the keys cannot be listed, and ciphers that use a different shift for each position (like Vigenère) flatten the frequencies.

Part IV

Attacking the toy scheme

The ciphertext of the toy scheme has no statistical structure to exploit (2.3), so the attack has to target the key. Here I play the attacker: I only know the public key Q and the ciphertext of Part I, and I want to read the message.

4.1

Brute force on the restricted key space

The private key is one of only K = 2 values, and the public key Q = kG is known to everyone. The simplest attack is therefore to compute the public key of every possible private key until one matches:

R ← G, k ← 1
while R ≠ Q: R ← R + G, k ← k + 1

Each step is one point addition, which is much cheaper than computing kG from scratch for every k. To compare R with Q without computing an inverse I check X = xQZ² and Y = yQZ³ directly in Jacobian coordinates. On average the search stops after K/2 steps, at most after K.

The search never looks at the ciphertext, and its answer is certain: Q = kG has exactly one solution in the range. Once k is known, the attacker decrypts exactly like the legitimate receiver. 

function* bruteForce(Q, limit) {
  let R = O,
    k = 0n;
  for (;;) {
    for (let i = 0; i < 4096; i++) {
      k++;
      R = jAddAffine(R, G);
      const Z2 = (R[2] * R[2]) % p;
      if (R[0] === (Q[0] * Z2) % p && R[1] === (((Q[1] * Z2) % p) * R[2]) % p) return k;
      if (k >= limit) return null;
    }
    yield k;
  }
}

4.2

Baby-step giant-step

Brute force is linear in K. Shanks' baby-step giant-step algorithm (1971) trades memory for time. With m = ⌈√K⌉, every key k ≤ K can be written as k = i·m + j with 1 ≤ j ≤ m and 0 ≤ i ≤ m, and then Q − i·(mG) = jG:

baby steps: store jG for j = 1, …, m in a hash table
giant steps: Q, Q − mG, Q − 2mG, … until one is in the table
match at step i with jG  ⇒  k = i·m + j

This needs about 2√K point additions instead of K/2, at the cost of storing √K points. To look the points up they must be in the form (x, y), so I convert them in batches with Montgomery's trick: one inverse for every 2048 points instead of one each.

4.3

Two different attacks

Key search on the toy scheme Statistical attack on Caesar
What it exploits The small number of possible private keys. The ciphertext itself reveals nothing. The ciphertext: a fixed shift keeps the letter frequencies of the language.
What the attacker needs Only the public key Q to find k; the ciphertext only to read it afterwards. The ciphertext and a model of the language (the corpus).
How a key is recognised Exact check kG = Q: the answer is certain. Statistical score (χ², bigrams): the best key is the most likely one, and it can be wrong.
Effect of message length None: a one-character message is as easy as a book. Decisive: short texts fail, longer texts almost never (3.4).

Remedy Choose k from the full range. None within the cipher: 26 keys and a deterministic shift are built into it.

The Caesar cipher is broken by statistics: the attacker learns the key from regularities that the encryption fails to hide. The toy scheme is broken by counting: its ciphertext passes the statistical tests of 2.3, and the only problem is that there are too few keys. This is why the first weakness cannot be fixed by changing a parameter, while the second one can.

4.4

Why it fails against full-size keys

The cost of both attacks grows with the size of the key space, which is exponential in the number of bits. The table uses the speed measured on this computer, point additions per second, to estimate the expected time for larger keys.

Memory for baby-step giant-step counts 64 bytes per stored point. The last column assumes computers a million times faster than this one and a billion of them working together. The age of the universe is about 1.4 × 1010 years.

A properly configured scheme draws k uniformly from {1, …, n − 1} with a secure random generator, so K ≈ 2256. On secp256k1 no attack faster than the generic ones is known: the order n is prime, so the problem cannot be split into smaller ones (Pohlig–Hellman), and the curve does not belong to the special families for which the ECDLP can be moved to an easier problem. The best method is then Pollard's rho, which needs about √(πn/4) ≈ 2128 additions like baby-step giant-step but almost no memory.

2128 ≈ 3.4 × 1038 operations is out of reach even with the optimistic hardware of the last column, which would still need . Baby-step giant-step would also need to store 2128 points, far more than all the storage that exists, and brute force, at 2255 steps on average, is even further away. The same search that took a few seconds in 4.1 is therefore not a practical attack: its cost is fixed by the key space, and the key space of a real key is too large.

4.5

Where the weaknesses come from

Not every weakness of the toy scheme is caused by the small keys. Some come from the way the scheme itself is designed, and they would remain even with a full-size private key.

Attack Cause What it does
Brute force on k KEY SPACE Finds k in at most K additions (4.1). Impossible with K ≈ 2256.
Baby-step giant-step, Pollard's rho KEY SPACE Find k in about √K additions (4.2). With a full key this is 2128, which is the actual security level of secp256k1.
Precomputed table KEY SPACE The K possible public keys are the same for every user. One table of all of them, computed once (with 220 keys, about a million points), then breaks every user with a single lookup.
Weak or reused r DESIGN My implementation draws r from the full range. If it were drawn from a small range like k, the same brute force on C1 = rG would give r and then M = C2 − rQ without the private key. If the same r were used for every character, equal characters would give equal C2, and the ciphertext could be read with frequency analysis, like a substitution cipher.
Malleability DESIGN Nothing protects the integrity of the ciphertext. Whoever knows one character m can replace it with any m′ by sending C2 − M + M′, and blocks can be removed or reordered without being noticed.
Byte-by-byte blocks DESIGN The number of pairs reveals the exact length of the message, and the ciphertext is 66 times larger than the plaintext. Real schemes such as ECIES use the shared point only to derive a key for a symmetric cipher with authentication.

In summary, the restricted key space is the only reason the toy scheme can be broken by a search, and it is easy to remove: with k drawn from the whole range, the same attacks go from a few seconds to about 2128 operations. The design problems are of a different kind: they do not reveal the key, but they show that encrypting with a correct key is not enough, because how the message is split, how r is chosen and whether the ciphertext is authenticated also matter.

The Caesar cipher fails on both fronts at once: 26 keys can be listed by hand, and even with more keys a deterministic substitution would still pass the statistics of the language to the ciphertext. Part III shows that a few dozen letters and a reference corpus are enough to read it.

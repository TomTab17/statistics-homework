Homework 1 · Public-key cryptography

Private key → public key

In Ethereum the public key is derived from the private key through elliptic-curve scalar multiplication, Q = kG. Computing Q from k is easy and deterministic, whereas recovering k from Q requires solving the Elliptic Curve Discrete Logarithm Problem (ECDLP). On this page I rebuild the mechanism on a small toy curve and then study some statistical properties of the points it produces.

1.1

The toy curve

Ethereum uses the curve secp256k1, with equation y² = x³ + 7 defined over a very large prime field (about 2²⁵⁶ elements). For this exercise I keep the same equation but work with the integers modulo 17:

E :  y² ≡ x³ + 7  (mod 17)

A point of the curve is a pair (x, y) with both coordinates in {0, …, 16} that satisfies the equation. Checking all 17 × 17 pairs gives 17 points, which are the ones drawn in the figure. The "curve" is therefore no longer a continuous line, but a finite set of points on a grid.

To make the addition work, one extra point is needed: the point at infinity O, which plays the role of zero. This gives 18 elements in total. The points are also symmetric: if (x, y) is on the curve then (x, 17 − y) is too, since (−y)² = y². This second point is the opposite of the first one, written −P.

1.2

Base point and private key

Two ingredients are needed. The base point G is public and the same for everyone, while the private key k is an integer known only to its owner.

BASE POINTG = (1, 5)
PRIVATE KEYk = 6
PUBLIC KEYQ = kG

First I check that G really is on the curve: 5² = 25 ≡ 8 and 1³ + 7 = 8 (mod 17), so it is. The public key is simply G added to itself k times:

Q = kG = G + G + … + G (k terms)

Before computing anything, it is therefore necessary to define what adding two points means.

1.3

Point addition

To add P = (x₁, y₁) and Q = (x₂, y₂) the idea is geometric: draw the line through P and Q, find the third point where it meets the curve, and reflect it (y → 17 − y). The result is R = P + Q = (x₃, y₃). In formulas, with λ the slope of the line:

λ = (y₂ − y₁) · (x₂ − x₁)⁻¹ if P ≠ Q (chord)
λ = 3x₁² · (2y₁)⁻¹ if P = Q (tangent, “doubling”)
x₃ = λ² − x₁ − x₂
y₃ = λ(x₁ − x₃) − y₁ all modulo 17

Since all arithmetic is modulo 17, there are no fractions: dividing by a means multiplying by its inverse a⁻¹, i.e. the number with a · a⁻¹ ≡ 1. For example 10⁻¹ = 12, because 10 · 12 = 120 ≡ 1. There are also two special cases: P + O = P and P + (−P) = O.

The figure shows the example G + 2G: the small dots are the 17 points of the line modulo 17, and exactly three of them lie on the curve. This is the code I wrote: 

const p = 17;                          // field modulus
const O = null;                        // point at infinity (neutral element)
const mod = a => ((a % p) + p) % p;    // result always in 0 … p−1

// Modular inverse by Fermat's little theorem: a⁻¹ ≡ a^(p−2) (mod p)
function inv(a) {
  let r = 1;
  for (let i = 0; i < p - 2; i++) r = mod(r * a);
  return r;
}

// Point addition on y² = x³ + 7 (mod p). Points are [x, y] or O.
function add(P, Q) {
  if (P === O) return Q;                                   // O + Q = Q
  if (Q === O) return P;                                   // P + O = P
  const [x1, y1] = P, [x2, y2] = Q;
  if (x1 === x2 && mod(y1 + y2) === 0) return O;           // P + (−P) = O
  const lambda = (x1 === x2)
    ? mod(3 * x1 * x1 * inv(2 * y1))                       // tangent (doubling)
    : mod((y2 - y1) * inv(x2 - x1));                       // chord
  const x3 = mod(lambda * lambda - x1 - x2);
  const y3 = mod(lambda * (x1 - x3) - y1);
  return [x3, y3];
}

// Returns [G, 2G, 3G, …, kG] by repeated addition.
function multiples(G, k) {
  const list = [];
  let R = O;
  for (let i = 1; i <= k; i++) { R = add(R, G); list.push(R); }
  return list;
}

// Returns kG by double-and-add: about log2(k) doublings and at most as many additions.
function mulDA(G, k) {
  let R = O;
  for (const bit of k.toString(2)) {
    R = add(R, R);                                         // doubling
    if (bit === "1") R = add(R, G);                        // addition
  }
  return R;
}

The toy public key

This is the list printed by the program, G, 2G, …, kG. The last point is the public key:

TOY PUBLIC KEY

Computing it took k − 1 = 5 additions. Adding G one at a time works here, but it is too slow for a large k. A faster method is double-and-add, which I implemented in the mulDA function above: it needs about log₂ k doublings and at most as many additions. For example 1000 = 1111101000 in binary, so 1000G takes 9 doublings and 5 additions instead of 999 additions:

Going backwards means finding how many times G was added to obtain Q. On the toy curve a few attempts are enough, but on secp256k1 there are about 2²⁵⁶ possibilities and no efficient method is known.

2.1

Repeating the experiment

The first thing I notice when computing kG for larger and larger k is that the sequence starts repeating. The smallest n such that nG = O is called the order of G; here n = . After that the points come back in the same order: (k + n)G = kG.

This means that only k = 1, …, n − 1 give different public keys, so these are the values I use as the sample. The curve has 18 elements and the order of a point always divides 18. The base point of the exercise, G = (1, 5), has order 9 and only reaches half of the curve, while for example (6, 6) has order 18 and generates all of it.

2.2

Distribution of the coordinates and frequency of individual values

The two histograms count how many times each value from 0 to 16 appears as an x or as a y coordinate among the points.

y: no value appears twice. The reason is that modulo 17 every number has exactly one cube root (the map x → x³ is a bijection), so once y is fixed there is only one possible x.

x: the values come in pairs, because P and −P have the same x. The only exception is x = 3: the point (3, 0) is its own opposite, and it only shows up when the base point has even order. Only of 17 values of x appear at all (9 over the whole curve), so the coordinates are clearly not uniform on {0, …, 16}.

2.3

Distribution of bits

I encode each coordinate on 5 bits (the values go up to 16), so every point becomes a string of 10 bits. The chart shows, for each bit position, the fraction of points where that bit is 1. A truly random bit string would give 0.5 everywhere.

Some positions are close to 0.5, but the highest bits are very unbalanced. Bit 4 is 1 only for the value 16, and x = 16 never appears on this curve. This bias is therefore caused by the binary representation of the numbers (17 is not a power of two, so bit 4 is set by just one value) and not by the scalar multiplication itself.

2.4

Apparent uniformity

Uniformity has to be assessed on the right set. Inside one period, the map k → kG is a bijection between {0, …, n − 1} and the points generated by G: every point comes from exactly one k. So if the private key is chosen uniformly at random, the public key is exactly uniform over those points.

This is not an empirical result: it follows directly from the group structure. What is not uniform, as shown in 2.2 and 2.3, is the representation of the points as coordinates and bits.

Correlation between input and output

The scatter plots compare the input k against with each coordinate of the output; r is the Pearson correlation coefficient.

For x I get r = , and it is exactly zero for every base point. The reason is that the plot is symmetric around k = n/2: the point (n − k)G = −kG has the same x as kG. For y I get r = , but this number changes with the base point and flips sign if G is replaced by −G, so with so few points it carries no real meaning.

There is therefore no linear trend between k and the coordinates. Input and output are nevertheless linked by an exact algebraic rule, (k₁ + k₂)G = k₁G + k₂G, and the symmetry in the plot is one visible consequence of it.

2.6

Avalanche-like behaviour

A function has the avalanche effect if changing one bit of the input changes, on average, half of the output bits. To test it, I take every k in the sample, flip one bit of k at a time and count how many of the 10 output bits change. Pairs that involve O are skipped, since it has no coordinates. If the new key is outside the period (for example 13 when n = 9) I reduce it modulo n, because (k + n)G = kG.

On average of the output bits change. However, 50% is not the right reference here: two different points picked at random from the same set differ on average in of their bits, because some bit positions are almost always the same (2.3). Measured against this baseline, nearby keys behave roughly like unrelated random points.

The resemblance, however, is only superficial. The two outputs are connected by a simple relation, (k + 1)G = kG + G, so anyone can get the public key of k + 1 from the public key of k without knowing k. A good hash function must not exhibit any such relation between similar inputs.

Part III

Discussion

Which of these properties matter for a one-way function like k → kG, and which ones are typical of cryptographic hash functions?

Property One-way function k → kG Cryptographic hash function
Determinism ESSENTIAL
The same k must always give the same Q, otherwise a key pair could never be reproduced. 		ESSENTIAL
The same message always gives the same hash.
Easy forward, hard backward ESSENTIAL
This is the defining property. Inversion is the ECDLP: trivial on the toy curve (n ≤ 18), but impossible in practice on secp256k1, where the best known attacks need about 2¹²⁸ operations. 		ESSENTIAL
Here it is called preimage resistance. The difference is that it does not rely on a hard math problem, but on the lack of any exploitable structure.
Uniformity of the output MEANINGFUL on the group
A uniform k gives a uniform point among those generated by G (2.4), so no public key is more likely than another. Uniform coordinates or bits are not needed, and in fact they are not uniform (2.2, 2.3). 		ESSENTIAL on the bits
The output should look like a random bit string: balanced bits and all values equally likely are part of the design.
Input–output correlation PARTLY
There should be no statistical trend that helps guess k from the coordinates. But there is an exact algebraic link, (k₁ + k₂)G = k₁G + k₂G, and it is there on purpose: key exchange and digital signatures are built on it. 		ESSENTIAL
There must be no usable relation of any kind, statistical or algebraic, between inputs and outputs.
Avalanche effect NOT REQUIRED
Outputs of nearby keys look unrelated (2.6), but they are connected by a public relation. Security does not depend on this. 		SPECIFIC
One of the main design goals: flipping one input bit should change each output bit with probability ½.
Collisions NOT APPLICABLE
For k in {0, …, n − 1} the map is one-to-one (2.1), so two different private keys never give the same public key. 		SPECIFIC
A hash compresses inputs of any length into a fixed length, so collisions must exist. Collision resistance means that none can be found in practice.

In summary, what matters for elliptic-curve scalar multiplication is that it is deterministic, fast in the forward direction, hard to invert, and that a uniform private key gives a uniform public key over the group. All of these come from the group structure, and the experiments show them even on a curve with only 18 elements. The only exception is hardness, which only appears at real cryptographic sizes.

Balanced bits, uniform coordinates, the avalanche effect and collision resistance are instead properties of hash functions. Scalar multiplication only appears to have some of them, and it keeps an algebraic structure on purpose, which is exactly what a hash function has to destroy. This is consistent with how Ethereum works: the public key is then passed through the Keccak-256 hash to get the address.
